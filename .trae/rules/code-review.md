# 代码评审深化规范

适用范围：全仓库所有代码变更（apps/ / services/ / packages/ / docker/ / design/ 等）。
本规范定义代码评审的目的、必查项、评论标签、PR 大小、Approval 规则与 SLA，所有 PR 须遵守。

## 一、Review 的五大目的

| 目的 | 说明 |
|------|------|
| 质量保证 | 发现缺陷、边界情况、安全漏洞，把好合并前最后一道关 |
| 知识共享 | 让团队成员了解变更内容，降低 bus factor（单点知识风险） |
| 风格一致 | 统一代码风格与模式，降低后续维护成本 |
| 架构守护 | 防止架构腐化，确保变更符合设计文档（D01–D46）与 ADR 决策 |
| 培养工程师 | 通过反馈帮助成员成长，建立技术讨论文化 |

## 二、Reviewer 必查项（每个 PR）

每个 PR 评审时，Reviewer 须逐项检查以下五大维度：

### 2.1 业务正确性

- 边界情况：空值（`null` / `undefined` / `None`）、空集合、超长字符串、负数/零值。
- 并发场景：共享状态是否有竞态条件，事务边界是否正确。
- **AI 结果人工复核流程**：涉及 AI 调用的变更，须确认结果按风险等级进入人工复核流程（见设计约束红线），AI 不替代注册建筑师/工程师的专业审签。

### 2.2 安全

- 无密钥提交：检查是否将 API Key / 密码 / Token 硬编码进代码或配置。
- 输入校验：防 SQL 注入（参数化查询）、防 XSS（输出转义）、防 SSRF（URL 白名单）。
- 权限校验：前端权限仅作体验控制，**后端必须再次查询权限**，不信任前端传入的角色字段。
- AI Provider 接入合规：外部 AI Provider（EVAI/小库 AI/建筑学长）在 V1 维持 ManualHandoff，未获正式 API/许可不得自动接入（见 OD-05 决策）。

### 2.3 性能

- 无 N+1 查询：循环内禁止发数据库查询，须用 JOIN 或批量查询。
- 无大对象堆积：避免内存中持有完整大文件，流式处理设计文件。
- Bundle size 不超预算：前端新增依赖须评估包体积，主 Bundle 不超预算阈值。

### 2.4 测试

- 新代码有测试覆盖：覆盖正常路径 + 异常路径（错误码、边界值）。
- 测试名描述行为：如 `should_return_404_when_design_file_not_found`，而非 `test1`。
- 可独立运行：测试不依赖外部网络（用 mock / TestContainers），`pnpm test` 可独立通过。

### 2.5 文档

- CHANGELOG 更新：用户可感知的变更须更新 CHANGELOG。
- API 变更同步 OpenAPI：契约变更须更新 `design/r2-contract-catalog/` 与 OpenAPI spec。
- 重大架构变更有 ADR：架构决策须在 `design/decisions/` 记录 ADR。

## 三、Conventional Comments 标签（必加）

每条评审评论**必须**以标签前缀开头，标明评论性质，便于作者判断优先级与处理方式：

| 标签 | 含义 | 示例 |
|------|------|------|
| `praise:` | 赞扬，认可好的设计或实现 | `praise: 这个错误处理抽象得很清晰，复用性很好` |
| `nitpick:` | 挑剔，小问题，非阻塞，作者可酌情处理 | `nitpick: 变量名 `d` 建议改为 `designFile`` |
| `suggestion:` | 建议，提出改进方案但非强制 | `suggestion: 这里可以用 Record<K,V> 简化类型定义` |
| `issue:` | 问题，必须修改才能通过（阻塞项） | `issue: 缺少 null 检查，当 user 为 null 时会 NPE` |
| `question:` | 提问，需要作者解释澄清 | `question: 这里为什么用同步调用而非异步？` |
| `thought:` | 思考，启发式讨论，非要求 | `thought: 未来如果扩展到多租户，这个设计需要调整` |
| `chore:` | 杂项，非代码逻辑相关（如 CI 配置） | `chore: 这个 workflow 的 name 字段拼写有误` |
| `note:` | 备注，补充上下文信息 | `note: 这段逻辑参考了设计文档 D28 的约定` |

- 阻塞项（`issue:`）须明确指出，作者修改后 Reviewer 须复核确认。
- 非阻塞项（`nitpick:` / `suggestion:` / `thought:`）作者可选择性采纳，但应回复说明理由。

## 四、PR 大小规范

| 类型 | 行数 | 处理方式 |
|------|------|----------|
| 小 PR | ≤ 500 行 | 建议，优先采用 |
| 中 PR | 500 – 1500 行 | 可接受，须有清晰描述 |
| 大 PR | > 1500 行 | **强制拆分**，否则拒绝评审 |

### 4.1 拆分维度

大 PR 须按以下维度拆分为多个小 PR：

- **按分层**：数据层（Entity/Repository）→ 业务层（Service）→ UI 层（Controller/前端），分层提交。
- **按 feature**：一个功能拆为多个子功能，每个子功能独立 PR。
- **重构与功能分离**：纯重构（如重命名、提取函数）与功能变更**必须分两个 PR**，避免混合干扰评审。

## 五、Approval 规则（项目特化）

| PR 类型 | Approval 人数 | 附加要求 |
|---------|---------------|----------|
| 普通 PR | 1 人 approve | — |
| 契约变更（API/Event/File Schema） | 2 人 approve | 须参考 `design/r2-contract-catalog/`，确认稳定 ID 一致 |
| AI 安全红线相关 | 2 人 approve | 须确认人工复核流程已落地（见设计约束红线） |
| 部署画像（Hybrid-Site）相关 | 2 人 approve | 须参考 `design/r2-deployment-profile/`，确认 Worker 画像一致 |

- 契约变更涉及 `design/r2-contract-catalog/` 中已分配的稳定 ID，修改须同步更新目录。
- AI 安全红线相关包括：AI 调用流程、风险等级判定、人工复核入口、AI Provider 接入。
- Hybrid-Site 相关包括：Worker 镜像分发、客户站点同步、RPO/RTO 配置、DB 迁移兼容性。

## 六、Review SLA

| PR 类型 | 首响应时效 | 说明 |
|---------|-----------|------|
| Hotfix | < 30 分钟 | 紧急修复，优先评审 |
| 小 PR（≤ 500 行） | < 4 小时 | 日常迭代主力 |
| 中 PR（500–1500 行） | < 1 天 | 须留足评审时间 |
| 大 PR（> 1500 行，已拆分） | 协商 | 由作者与 Reviewer 协商排期 |

- 超时未响应时，作者可在群内 @ Reviewer 催办，或在 PR 中标注 `blocked-on-review`。
- Reviewer 无法评审时，须及时说明并转交他人，**禁止静默拖延**。

## 七、禁止项

- **禁止**评论人（只评论代码）：对事不对人，禁止人身攻击或贬低性表述。
- **禁止**挑剔小风格：缩进、引号等由 lint 自动处理，评审不纠结（用 `nitpick:` 标签且不阻塞）。
- **禁止**静默拖延：无法评审须及时转交，不让 PR 卡住。
- **禁止**只看新增代码：须结合上下文查看修改对周边逻辑的影响。
- **禁止**盖橡皮章 LGTM：Approval 必须附**至少 1 条 Conventional Comment**（即使是 `praise:`），禁止无内容批准。
- **禁止**巨型 PR：> 1500 行必须拆分，否则直接拒绝评审。
- **禁止**PR 描述空或混合多目的：PR 描述须说明"为什么改"（动机）+ "改了什么"（范围），一个 PR 只做一件事。
