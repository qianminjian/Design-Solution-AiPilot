# 子 Agent 内存管控规则

> 来源：2026-07-23 内存爆炸事件总结

## 问题背景

本机内存限制为 16GB，并行启动 3 个以上子 agent 时，每个 agent 加载大量上下文（源码、文档、工具描述）导致内存占用达到 3-4GB/agent，触发 macOS `vm-compressor-space-shortage` → 系统强制重启。

## 核心原则

### 1. 单一职责：一个 Agent 只做一件事
- 每个 agent 的任务描述必须清晰、单一，避免"同时做 X 和 Y"的复合任务
- 任务描述长度限制：≤ 300 字符（含换行）
- 禁止在一个 agent 中加载多个模块的源码

### 2. 分批加载：按需读取，用完释放
- **绝对禁止**一次性 Read 整个框架或目录
- **绝对禁止**一次性 Read 超过 3 个源码文件
- 文件读取必须按需求分批进行：先读取关键文件，完成分析后再读取相关文件
- 每处理完一个文件后，立即执行写入操作，释放内存

### 3. 并行限制：严格控制并发数
- **绝对禁止**并行启动超过 **3 个**子 agent
- **绝对禁止**并行启动超过 **2 个**涉及大量源码加载的 agent
- **绝对禁止**在内存使用率接近 90% 时启动任何子 agent
- 推荐模式：串行执行或 2 个 agent 并行

### 4. 内存感知：实时监控与熔断
- 在启动新 agent 前，检查系统内存状态
- 如果可用内存 < 4GB，暂停所有 agent 启动，等待当前任务完成
- 如果可用内存 < 2GB，立即停止所有非关键 agent

## 实施策略

### 策略 A：串行执行模式（推荐）

适用于需要上下文传递的任务链：

```
任务 A → 完成 → 任务 B → 完成 → 任务 C → 完成
```

- 优点：内存占用最低（始终只有一个 agent）
- 适用场景：需要逐步分析的复杂任务、依赖前序结果的任务链

### 策略 B：双工并行模式

适用于完全独立的任务：

```
任务 A（前端页面）        任务 B（后端 API）
    ↓                         ↓
  完成                      完成
```

- 限制：最多 2 个 agent 并行
- 优点：在内存安全的前提下提高效率
- 适用场景：前后端独立开发、不同模块的测试修复

### 策略 C：分块串行模式

适用于大型任务的拆分：

```
阶段 1: 读取文件 A → 处理 → 写入结果 → 释放内存
阶段 2: 读取文件 B → 处理 → 写入结果 → 释放内存
阶段 3: 读取文件 C → 处理 → 写入结果 → 释放内存
```

- 每个阶段作为独立任务串行执行
- 强制在阶段间释放内存
- 适用场景：大型文档生成、多文件重构

## Agent 任务描述规范

### 4.1 任务描述模板

```
[任务类型]: [简短描述]

背景：[1-2 句话说明上下文]
目标：[明确的输出目标]
输入：[必须的输入文件/数据，按优先级排序]
输出：[必须的输出文件/数据]
约束：[技术限制、安全要求]
步骤：[1-3 个关键步骤，避免详细指令]
```

### 4.2 禁止的描述模式

- ❌ 禁止："创建完整的 X 功能，包括 A、B、C、D 模块"
- ❌ 禁止："读取所有相关源码并实现 Y"
- ❌ 禁止："完成 Z 的全部开发"

### 4.3 推荐的描述模式

- ✅ 推荐："创建 X 模块的 Controller，包含 A 和 B 两个端点"
- ✅ 推荐："修复 Y 测试文件中的 Mockito 兼容性问题"
- ✅ 推荐："实现 Z 功能的第一步：读取现有接口定义"

## 文件读取限制

### 5.1 单次读取限制

| 操作类型 | 单次最大数量 | 说明 |
|---------|------------|------|
| Read 源码文件 | 3 个 | 必须按优先级分批读取 |
| Read 配置文件 | 2 个 | pom.xml / package.json / docker-compose.yml |
| Read 设计文档 | 1 个 | 设计文档通常较大，需单独处理 |
| LS/Glob | 无限制 | 仅获取文件列表，不加载内容 |

### 5.2 内存阈值检查

在启动 agent 前执行以下检查：

```bash
# 检查可用内存（MacOS）
available_memory=$(vm_stat | grep free | awk '{print $3}' | tr -d '\.')
available_mb=$((available_memory * 4 / 1024))

if [ $available_mb -lt 4096 ]; then
    echo "警告：可用内存不足 4GB，建议等待当前任务完成"
fi

if [ $available_mb -lt 2048 ]; then
    echo "错误：可用内存不足 2GB，禁止启动新 agent"
    exit 1
fi
```

## 特殊场景处理

### 6.1 大型设计文档读取

设计文档（`design/D00-D46*.md`）通常较大，处理时：

- 仅读取相关章节文件（通过 `design/INDEX.md` 定位）
- 使用 `offset` 和 `limit` 参数分段读取
- 读取后立即分析，不保留完整内容在内存中

### 6.2 多模块测试修复

当需要修复多个模块的测试时：

- 每个模块作为独立任务串行执行
- 完成一个模块的测试修复后，验证通过再进行下一个
- 禁止同时加载多个模块的源码

### 6.3 CI 配置生成

创建 CI 配置时：

- 每个工作流文件单独创建（ci.yml / docker-build.yml / e2e.yml / security-scan.yml）
- 先创建简单的工作流，再创建复杂的
- 避免一次性生成所有配置

## 违规处理

### 7.1 警告级别

- 首次违反：记录到任务日志，提醒用户
- 再次违反：暂停任务，等待用户确认后继续

### 7.2 严重违规

- 导致系统崩溃：自动切换为串行模式，后续所有任务串行执行
- 连续违规：禁用子 agent 功能，改用直接执行模式

## 工具使用约束

### 8.1 禁止的操作

- ❌ 禁止：使用 `search` agent 搜索整个代码库
- ❌ 禁止：使用 `Read` 工具一次性读取超过 3 个文件
- ❌ 禁止：使用 `Glob` 匹配超过 100 个文件
- ❌ 禁止：使用 `RunCommand` 执行大量内存密集型操作（如 npm install）

### 8.2 推荐的操作

- ✅ 推荐：使用 `LS` 先查看目录结构
- ✅ 推荐：使用 `Grep` 精确定位代码
- ✅ 推荐：使用 `SearchCodebase` 进行精准搜索
- ✅ 推荐：使用 `RunCommand` 执行轻量级命令（如 git status、grep）

## 监控与报告

### 9.1 内存监控

每次启动 agent 前，记录当前内存状态：

```
[时间戳] Agent 启动前内存状态：总内存 X GB，已用 Y GB，可用 Z GB
```

### 9.2 任务完成报告

每个任务完成后，记录资源消耗：

```
[时间戳] 任务完成：[任务名称]，耗时 X 秒，内存峰值 Y GB
```

### 9.3 异常报告

当检测到内存异常时，立即报告：

```
[时间戳] ⚠️ 警告：内存使用率达到 85%，当前任务可能受影响
[时间戳] ❌ 错误：内存不足，任务终止
```
